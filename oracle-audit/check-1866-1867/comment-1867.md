Cross-check of this PR together with #1866 against the hardware, continuing the audit on #981. The kernels of the 26 execution tests the audit found sensitive to `DX10_CLAMP` or `IEEE_MODE` (28 kernels, 16,944 result cells per mode) ran through the recompiler of ef4dca9a (the recompiler tree of `main` at the merge, 42e91486, before #1878) on an RTX 3080 (driver 615.71.09) and on the RADV iGPU (Mesa 26.2.4), Linux (CachyOS, kernel 7.2.9), Release build with CI's flags, with `GuestContext::floatMode` set to the titles' mode (`FLOAT_MODE` 0xc0, `DX10_CLAMP` 1, IEEE 0), to no mode, to `DX10_CLAMP` 0, to IEEE 1 and to the oracle's former implicit mode (0xf0, IEEE 1), and were compared bit for bit with the oracle in the same mode. Per-cell data, driver and the replay harness with its `REPLAY_MODE` setting: https://github.com/SleglJan/AnyPS5/tree/audit/oracle-2026-10-08/oracle-audit/check-1866-1867.

- **No mode gives the titles' mode** in every cell on both hosts. A cell whose oracle value does not depend on a field does not move on the hosts when that field changes either (29,200 host cells for `DX10_CLAMP`, 31,910 for `IEEE_MODE`).
- **`DX10_CLAMP` (#1866).** 354 cells in 11 kernels change with the field on the oracle. 58 are in three of the four kernels with a clamped f64 result (DivisionOutputModifiers 14, DivisionResultModifiers 39, F64Transcendental 5); those four (F64Conversions too, with no sensitive cell) throw with `DX10_CLAMP`=0, as #1866 says. Of the other 296, RADV matches the hardware in 292 and returns the sNaN quieted in 4 (Float16TernaryClamp); NVIDIA matches in 204 and returns an all-ones NaN (0x7fffffff, 0x7fff in f16) in 92. No other difference.
- **`IEEE_MODE` (this PR).** 989 cells in 22 kernels change with the field. The four re-pinned tests match the hardware bit for bit with IEEE 1, and with IEEE 0 in all but Division's 10 `v_div_fmas_f32` cells, where the driver's fma returns the input sNaN quieted (0x7fc00001 for 0x7f800001; ternary arithmetic whose NaN bits the description leaves to the driver): DivFixupF16 21 cells, SdwaLdexpF16 36, Vop1FloatUnary 118, Division 21. With IEEE 1, 9 cells differ, Float16TernaryClamp's `v_min3/max3/med3_f16 clamp` with a NaN operand (the f16 min/max rule the TechnicalDebt entry lists as single-mode), and 40 more are NaN-payload differences on RADV (F32OutputModifier 21, Vop3CubeClamp 12, Float16Misc 4, Vop3PackLdexp 3), 53 on NVIDIA. In the titles' mode 39 cells differ: F64Arithmetic 14 (`v_min_f64`/`v_max_f64` return the quieted sNaN where the hardware returns the other operand) and F64Rounding 25 (`v_cvt_f32_f64 mul:2`, the output modifier the hardware applies to the f32 result, as noted on #1851). NaN-payload differences: 94 on RADV, 119 on NVIDIA (F32OutputModifier 21 and Float16Misc 4 more); 71 of the 94 are in the f64 tests (F64Arithmetic 21, F64Division 15, F64NanConversions 13, F64DivisionModifiers 10, F64Transcendental 8, F64Rounding 3, F64Conversions 1), where the tables hold the quieted NaN of IEEE 1 and both hosts produce it in every mode: 43 from the f64 emitter's unconditional quieting (`Quiet` in SpirvAluEmitterFloat64.cpp, behind add, mul, fma, ldexp, min, max and the unary ops), 11 from `v_div_fixup_f64`'s in Float64Instructions.cpp, 17 in the f32/f64 conversions. Those tables were captured in the same implicit mode as the four this PR pins; as a follow-up, the same `floatMode` line would make them declare it.

The 28-kernel run predates the #1878 merge; #1878 changes only `v_fma_mix_f32`, and MixPrecision rerun after it gives the same bits in every cell. Hardware: Ryzen 7950X3D iGPU (gfx1036, RDNA2) through `tools/hw-oracle` under hsa-rocr 7.2.4; not the PS5's gfx1013.
